# 本地优先：我们和 AstrBot 的取舍差异

AstrBot 是为**云端模型**适配的：模型延迟由网络决定，上下文成本由 token 计费决定，
所以它优化的是上下文组织、插件生态、平台兼容。本地模型在它那里是"顺手兼容"。

本地部署时，决定体验的完全是另一组变量：

- **KV 缓存是否命中**（决定预填充是 10ms 还是 2.5s）
- **显存余量**（顶到天花板时生成速度腰斩）
- **并行槽位**（多请求落到不同 slot，缓存互相作废）
- **生成速度**（思考 token 和正文 token 一个速度，思考多久就慢多久）

这些在云端全都不存在，所以也不能指望云端方案在这一层做优化。
**本项目的地板，应该是 AstrBot 的天花板。**

## 踩过的坑与实测收益

| 改动 | 之前 | 之后 | 依据 |
|---|---|---|---|
| system 保持静态，时间/群/说话人挪进 user 消息 | 每条消息 system 都变 → 缓存全废 | 前缀稳定，可复用 | 改 system 一个字：1800ms vs 170ms |
| 上下文窗口从"滑动 100 条"改成"锚点窗口"（60%~125% 浮动） | 每条都把最旧一条挤掉，前缀位移，全量重算 1668 token | 400 条消息里窗口只重锚 6 次 | prompt eval 2526ms → 170ms |
| 模型请求串行（后放宽为 per-session + 上游槽位数上限） | 并发抢显存，22~28 t/s | 单请求 45~55 t/s | llama.cpp eval time |
| 思考计入 `max_tokens`，用 `thinking_budget` 做软闸 | 思考 985 吃光 1024，正文为空 | 超预算掐断，无思考模式重答 | 2026-11-02 21:53 空回复 |
| 输入输出统一 `at 名字(QQ)` 标记 | 模型照抄 `@`，输入输出语义打架 | 入站展开、出站还原 | 2026-11-02 21:26 答错人 |
| 不跨发言人合并轮次 | 12 条不同人的消息并成一个 user 轮次，模型把最后说话的人当成作者 | user 一律独立轮次，只合并 assistant | 2026-11-02 21:57 乱答 |
| 历史行带 `[HH:MM]` | 模型分不清"刚才"和"两小时前" | 有时间参照 | 对齐 AstrBot 的 `[昵称/时间]` 转录 |
| 提示词加一句"思考别复述人设、别用英文分析" | 5 个问题平均 342 思考 token，最长 711（14.5s） | 平均 234，最长 292 | 同一提示词对照跑两轮 |
| `at 名字(QQ)` 正则把括号里的号一起吃 | 模型照学历史，发成 `at 贰叔(1140853441) (1140853441)` | 一个 at 段，没有残留正文 | 2026-11-02 23:08 日志 |

## 本机实测的运行时数字

LM Studio 0.4.28，Vulkan，qwen3.8-27B Q4_K_M，32768 上下文 / 4 槽位：

| 指标 | 实测值 | 说明 |
|---|---|---|
| **每请求固定开销** | **约 2.5 秒** | 和提示词长度、输出长度都无关：热缓存下只要 1 个 token 也是 2.5s。这是本地栈的地板 |
| 预填充 | 400~620 t/s | 2000 token 约 3.3s，6000 token 约 9.2s |
| 缓存命中后的预填充 | 只剩增量（约 170 token / 670ms / 4 token 时 157ms） | `f_keep` 0.89~0.90，6000 token 的提示词也能命中 |
| 生成 | 45~65 t/s | 思考 token 和正文 token 同价，300 token 思考 ≈ 5~7s |
| 选槽规则 | 先按前缀相似度（阈值 0.1），否则按 LRU 挑**空**槽 | 挑到空槽 = 全量重算，日志里是 `selected slot by LRU, n_tokens = 0` |
| prompt cache 条目 | 单条 770MB~1.2GB 级别，显存紧就淘汰 | `making room for prompt cache entry, removing oldest entry` |

一条普通回复的时间账（`in=2367`，思考 272，正文 19）：2.5s 固定开销 + 3.9s 预填充 + 5.2s 思考 + 0.4s 正文 ≈ 12s。
**想进 5 秒只有两条路**：砍思考（每 100 token ≈ 2s），或者换更快的卡/更小的模型。
预填充只在缓存没命中时才算钱，固定开销和思考则每条都要付。

## 教训

1. **别拿两次不同负载下的测量做对比。** 16k 上下文那个"提速一倍"是在我自己跑基准、又有两个群并发时测的，负载一换结论就翻车。
2. **先看 llama.cpp 的 `prompt eval time` 和 `eval time`**，再猜原因。日志里两者分得很清楚，比任何推测都准。
3. **AstrBot 的请求体是现成的教材**，LM Studio 的 server log 会完整记录每个请求，直接翻就能看出它怎么组织上下文。
4. 云端方案的长处（上下文管理、插件化）要学；短处（对本地资源无感知）必须自己补。
5. **"掐断重答"这类兜底，成本可能比它想省的时间还高。** 设兜底之前先算清两个数：
   原路走完要多久，兜底这条路从零开始要多久。算不清就别加。
6. **先量"固定开销"，再谈优化。** 每个请求 2.5 秒和提示词长度无关，这种钱省不掉，
   只能认清它，把预算花在真正会变的那几项上。
